## 2026-09-11：CSV 流式导入与基础数据画像

| 项目 | 内容 |
| --- | --- |
| GitHub Issue | [#5 完成 CSV 流式导入与基础数据画像](https://github.com/windgogo-qzj/better-data/issues/5) |
| Pull Request | [#11 完成 CSV 流式导入与基础数据画像](https://github.com/windgogo-qzj/better-data/pull/11) |
| 分支 | `feat/5-csv-import-profile` |
| 核心提交 | `6b32fa0 feat: 完善 CSV 导入与基础画像` |
| 当前阶段 | PR #11 已通过 GitHub Actions 并合并，Issue #5 已关闭 |

### 开发前审计

- 已有 `POST /api/projects`、流式文件写入、SHA-256 和 Polars 抽样画像雏形。
- 自动测试只有一个健康检查，不能证明上传、大小限制、哈希或画像行为正确。
- CSV 使用 `ignore_errors=True`，异常行可能被静默忽略，不符合“错误文件得到明确提示”的验收要求。
- 上传超限时只删除部分文件，会留下没有元数据的空项目目录。
- 返回模型缺少抽样状态和可直接展示的行预览。

### 本次实现

- 文件仍以 1 MiB 分块流式写入，同时计算 SHA-256 并执行大小上限检查。
- CSV 在进入 Polars 前检查 UTF-8/UTF-8 BOM、空文件、空表头和重复表头。
- 自动识别逗号、分号、TAB 和竖线四种常见字段分隔符。
- 关闭 Polars 的静默容错；解析失败返回包含恢复方向的中文错误。
- `DatasetProfile` 增加 `is_sampled` 和最多五行的 `preview_rows`。
- 超过画像上限时只使用前 N 行并返回明确抽样警告。
- 上传阶段失败且尚未生成 `project.json` 时，安全清理本次新建的项目目录。
- 数据画像失败时仍保留原始文件和 `failed` 项目记录，便于用户查看错误并恢复。

### 自动化验证

本地运行 `python -m pytest -q`，结果为 **9 passed**。覆盖：

1. CSV 上传、项目创建和项目列表。
2. 原始文件字节一致性与 SHA-256。
3. 字段数量、缺失值、抽样标记和行预览。
4. 分号分隔符识别。
5. 空文件、空表头、重复表头和非 UTF-8 编码。
6. 不支持的扩展名。
7. 文件超过上限后的错误响应和残留目录清理。

GitHub Actions 在 Windows 环境重新执行前端构建和后端测试，两个任务均通过。Actions 对仍使用 Node.js 20 运行时的第三方 Action 给出弃用提示；项目应用使用的 Node.js 版本仍为 22.13.0，该提示不影响本次验收。

### 关键决策

- **严格解析优先于静默修复**：导入阶段不猜测如何修复损坏行，避免无提示的数据丢失。
- **UTF-8 是 MVP 的明确边界**：其他编码先给出清晰错误，后续可在显式转码功能中安全支持。
- **画像保持有界**：读取 `sample_rows + 1` 行判断是否抽样，不为了精确总行数再次完整扫描大型 CSV。
- **错误项目可诊断**：成功保存原始文件后发生的画像错误保留项目；尚未完成上传的项目不保留。

### 已知限制

- MVP 暂不支持自动转码 GBK 等本地编码。
- 当前画像基于文件前部抽样，不代表全量精确统计。
- CSV 分隔符识别限定为逗号、分号、TAB 和竖线。
- Starlette 测试客户端在当前依赖组合下报告弃用警告，不影响测试结果；依赖升级应单独处理。

## 2026-09-11：项目库与本地项目生命周期

| 项目 | 内容 |
| --- | --- |
| GitHub Issue | [#1 建立项目库与本地项目生命周期](https://github.com/windgogo-qzj/better-data/issues/1) |
| 分支 | `feat/1-project-lifecycle` |
| 核心提交 | `fc9552e feat: 实现可配置项目库生命周期` |
| 当前阶段 | 本地实现与测试完成，等待远端 PR 与 CI |

### 开发前审计

- 后端项目库只能通过环境变量或默认路径指定，前端无法查询或修改。
- 首次运行不会要求用户确认数据保存位置。
- 项目库选择没有持久化配置，服务重启后无法恢复用户选择。
- 任意目录一旦被误选都可能被写入，缺少“这是 Better Data 项目库”的身份标记。
- 已有项目列表接口，但没有单项目详情接口。

### 本次实现

- 新增 `GET/PUT /api/settings/project-library`，查询和更新当前项目库。
- 首次运行返回 `needs_setup`，前端自动打开项目库设置，并在工作台持续提示确认。
- 项目库路径写入版本化的 `app-settings.json`，服务重启时自动恢复。
- 项目库写入 `.better-data-library.json` 标记；只接受空文件夹、已有标记的目录或兼容的旧项目库。
- 拒绝相对路径、普通文件和未标记的非空文件夹，避免覆盖无关数据。
- 切换项目库只更新后续读写位置，不移动、不合并、不删除原目录。
- 新增 `GET /api/projects/{project_id}`，并限制项目 ID 为 32 位小写十六进制格式。
- 前端增加首次设置提示、项目库设置对话框、路径错误说明和移动端设置入口。
- 设置保存后重新加载项目列表，界面同步显示新项目库的项目数量和存储占用。

### 自动化验证

本地后端测试为 **15 passed**，新增覆盖：

1. 首次运行的默认项目库和 `needs_setup`。
2. 项目库标记文件及其版本信息。
3. 选择结果写入配置并在 `ProjectStore` 重启后恢复。
4. 新项目写入所选项目库并能通过详情 API 读取。
5. 相对路径、普通非空文件夹和不存在项目的拒绝行为。
6. 切换失败时不修改原文件夹内容。

同时通过 `pnpm lint`、`pnpm build` 与 `git diff --check`。

### 关键决策

- **用户路径必须可识别**：项目库使用标记文件建立身份，避免仅凭目录名称猜测。
- **切换不是迁移**：修改项目库是低风险设置操作；数据迁移、合并和删除需要未来单独流程与确认。
- **配置使用原子替换**：项目元数据、库标记和全局设置都先写临时文件再替换，降低中断导致半写入的风险。
- **保留旧库兼容性**：已有包含合法 `project.json` 的默认库可以补写标记，不阻断早期版本数据。

### 已知限制

- 浏览器不能提供稳定、跨浏览器的原生目录选择能力，MVP 使用绝对路径输入；Windows 启动器阶段再接入系统文件夹选择器。
- 切换项目库后不会在界面中同时聚合多个库。
- 当前没有项目删除、回收站或迁移功能，这些属于后续生命周期能力。
